# ARCHITECTURE_RECOMMENDATIONS.md — рекомендации по улучшению (не меняя архитектуру)

> Дата: 15.11.2026. Ветка: `docs/architecture-recommendations`.
> Контекст: вопрос владельца «не пора ли на более мощную архитектуру ради стабильности
> и экономии токенов на правки?». Итог анализа — **архитектуру менять не стоит**
> (см. §1), но есть направления, которые реально упрощают жизнь (§2–§6).
> Файл документационный: версию НЕ бампит, рантайм НЕ трогает.

## 1. Почему «мощная архитектура» (React/TS/бандлер/несколько файлов) — вредна здесь

| Аргумент «за» перенос | Почему это не работает для проекта |
|---|---|
| «Один файл — это плохо, надо разбить на модули» | Ломает `sw.js ASSETS` (кэш поштучно), `tests/helpers.js` (извлекает inline `<script>` через `lastIndexOf`), философию «один статический файл, деплой = копирование» (AGENTS.md §2.2, REFACTORING.md §2.2). |
| «TypeScript поймает баги» | 387 тестов уже ловят больше, чем типы: vm-прогон РЕАЛЬНОГО inline-кода + 133+ клик-сценария. TS добавит сборку, `.d.ts`, транспайл — и всё это противоречит «без сборки». |
| «Стейт-менеджер даст порядок» | Дерево целей + 6 изолированных модулей («Хорошее сегодня», «Карта желаний», «Челлендж», «Достижения», «Настройки блоков», напоминание о сферах) уже разделены по `state.*`-кускам, каждый со своим рендером и хендлерами (AGENTS.md §1). Redux/Zustand в одностраничном PWA — лишний слой. |
| «Vite/Webpack ускорят правки» | Нет. Правки — это `replace`/`write_file` по точечным якорям + `npm test`. Сборка добавит шаг, который ломает PWA-обновление (CACHE_NAME, каноникизация `./index.html` в `sw.js`). |

Вывод: текущая «архитектура» — это и есть стабильность: один файл, офлайн-first SW,
487→387 тестов, CI, PATCH-бамп в 4 местах. Перенос на фреймворк вернёт боль
(сборка, деплой, версионирование, переписывание тестов под DOM-фреймворк) без
прироста качества продукта.

## 2. Рекомендации, которые реально экономят токены и снижают риск правок

Приоритет: от дешёвой к дорогой. Все пункты — документация/комментарии/тесты,
никакой не переписывают рабочий код (красные линии REFACTORING.md §2.1 держим).

### 2.1 Оглавление в `index.html` (0 риск, эффект сразу) — ✅ v1.4.67

В начало `<script>` добавить блок-комментарий «КАРТА КОДА» с приблизительными
номерами строк по секциям (`/* ===== Seed ===== */`, `Language`, `State`,
`Cloud sync`, `Render`, `attach*Handlers`, `wheel`, `wish`, `challenge`,
`achievements`, `goodToday`, `sphereReminder`, `hiddenBlocks`, `share`).
Правка: после каждой правки секции — сдвиг номера строк. Выгода: Ctrl+F вместо
`search_codebase` + догадок; меньше «слепых» чтений чанками.

### 2.2 JSDoc на публичные функции (низкий риск, накопительный эффект) — ✅ v1.4.67 (40 функций)

Аннотировать ~40 публичных функций, которые экспортируются в `EXPORT_SRC`
(`tests/helpers.js`) — это и есть «публичный API» приложения:
`computePercent`, `wheelPercent`, `wheelLeafFraction`, `sanitizeGoalTree`,
`loadState`/`saveState`, `resolve`/`validatePath`, `ensureWishMap`, `syncWishBoard`,
`flushCloudPush`, `resolvePushConflict`, `ensureChallenge`, `achievementsSectionHTML`,
`homeViewHTML`, `render` и т.д. Формат:

```js
/**
 * Доля листа в колесе: обычный лист 1/0, чек-лист done/total.
 * Пустой чек-лист = fallback на `done`. Архив не влияет.
 * @param {{done:boolean, children:Array, checklist?:Array}} leaf
 * @returns {number} 0..1
 */
function wheelLeafFraction(leaf) { ... }
```

Выгода: IDE-подсказки, меньше перечитываний, новые агенты быстрее находят
инварианты (липкий `totalGoalsAdded`, P3-A «архивная сфера = 100%»).

### 2.3 Описать `state` shape один раз, в комментарии у `loadState`/SEED — ✅ v1.4.67 (блок «SCHEMA STATE»)

Сейчас форма состояния разбросана по `emptyTemplate`, `SEED`, `ensure*`-функциям.
Один сводный JSDoc-комментарий «SCHEMA STATE» (поля, типы, инварианты, кто
обязан вызывать `ensure*` при подмене состояния — AGENTS.md §16 уже требует
`ensureChallenge` в 5 путях) сэкономит десятки чтений на сессию.

### 2.4 Оглавление CSS (13 секций уже есть — добавить индекс) — ✅ v1.4.67

В начало `<style>` — список секций с номерами строк. CSS 116 KB, 76 hover-правил
в гейте, 4 линии обороны тач-режима (AGENTS.md §14) — навигация по индексу
вместо grep по `@media` сэкономит вызовы.

### 2.5 Тест-сторожи для новых правил (профилактика, а не реактив) — ✅ v1.4.67 (docs-guard)

Паттерн проекта — «баг повторился 4 раза → сторож-тест». Добавлять сторож в
тот же коммит, что и правка, если правило нетривиальное (примеры из AGENTS.md:
`PAINTED_BY_ANCESTOR` для кнопок, `touch-mode`-нейтрализация ховеров,
`data-tip` на action-кнопках). Это дешевле любого рефакторинга: правка, которая
падает тестом, не доходит до пользователя и не требует отката.

### 2.6 Чек-лист «перед ответом» — в память агента, не в промпт каждый раз — ✅ v1.4.67 (AGENTS §4.0)

AGENTS.md §4 уже отличный чек-лист (7 пунктов). Дополнить его одним пунктом:
«правка только документация? → бамп НЕ нужен, коммит без версии». Сейчас
§3 AGENTS.md это покрывает, но явная развилка «документация vs рантайм» в начале
сессии сэкономит повторные вопросы владельца.

### 2.7 Экономия токенов на сессии (процесс, не код)

- Читайте `index.html` только чанками ≤150 строк по якорю (AGENTS.md §5 уже так
  говорит — держать правилом).
- `search_codebase` перед любым чтением — якорь, а не «на всякий случай».
- `npm test` отфильтрованным (`grep -E "^(✔|✖|ℹ (tests|pass|fail))"`), полный
  лог — только при падениях.
- Перед «проверяйте» — `git status -sb` (AGENTS.md §4.12): незапушенные коммиты
  = владелец тестирует старую версию.

## 3. Что НЕ делать (отклонено, не предлагать повторно)

См. REFACTORING.md §2.1: делегирование событий, консолидация UI-флагов в
`ui`/`authUi`, массовая замена `getElementById` на `on()`. И §2.2: не разносить
на файлы, не добавлять зависимости/сборку, не трогать колесо/липкие тоталы/
архив (P3-A), MINOR-бамп только по просьбе владельца, пуш — только владелец.

## 4. Итог

- Архитектура: **оставить как есть** (один файл, PWA, SW, Firebase-опционально).
- Инвестировать в: карта кода (§2.1), JSDoc на публичный API (§2.2), schema state
  (§2.3), индекс CSS (§2.4), сторож-тесты (§2.5), чек-лист агента (§2.6–2.7).
- Это даёт ~80% навигационной пользы «большой архитектуры» за ~5% усилий и без
  единой строки изменённого рантайма (версию бампить не надо).
